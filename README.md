# dsh-dbhub-live

**简体中文** · [English](README.en.md)

> 让 [DeepSeek Harness (DSH)](https://github.com/deepseek-ai/DeepSeek-Harness) 直接、安全地操作数据库：**凭据零知识**（密码永不经模型）+ **一次性进程执行**（无常驻服务、天然并发与多实例安全）+ 按工作区×环境的连接管理 + 浏览器配置页。

`dsh-dbhub-live` 是一个 DSH 插件，基于 [DBHub](https://dbhub.ai)（数据库 MCP 服务器）让模型直接查询数据库：模型只说「查哪个工作区的哪个环境」，插件在宿主侧解析真实连接并执行——**密码/连接串永远不会出现在模型能看到的地方**。每次调用都是独立的一次性 dbhub 进程，跑完即杀。

## ✨ 特性

- **凭据零知识** — 模型只见 `source` 句柄与元数据（类型 / 主机 / 端口 / 库名）；密码、用户名、完整 DSN 只在宿主侧存在；配置/修改密码时**在界面输入**，不经过模型。
- **一次性进程执行** — 没有常驻 dbhub 服务：每次调用 spawn 一条独立进程执行完即回收。单条查询挂掉只影响它自己；多任务并行、多个 DSH 实例同时跑互不干扰（无共享端口、无互杀）。
- **工具声明恒定 4 个** — `dbhub_configure` / `dbhub_list_sources` / `dbhub_execute_sql` / `dbhub_search_objects`，环境再多也不膨胀模型上下文。
- **按工作区 × 环境管理连接** — 一个工作区可配多个环境（default / prod / dev / test…），通过 `source` 值区分，互不混淆。
- **环境级只读 + 手动 SSH 隧道** — 每个环境可以单独**开启只读**（写操作由 dbhub 原生拒绝；模型只能开、不能关）或配置**手动 SSH 隧道**（密码/口令只在界面输入、不经模型；单跳 ProxyJump）。两者都需要 dbhub **1.4.0+**。隧道是否通可以用行编辑器里的「测试 SSH 隧道」**单独验证**，不必把隧道和数据库搅在一起猜。详见 [只读模式与 SSH 隧道](#-只读模式与-ssh-隧道)。
- **鉴权失败闭环** — 凭据或连接信息不对时，工具给出明确指引；模型引导你在界面更新密码（不会向模型索要密码），或你直接在设置卡片修改。**配置时自动试连**：说的是非敏感连接信息会先在宿主侧实测——可连通就直接生效（免密码库零输入），只差密码时弹窗只问「账号（未知时）+ 密码」，不再让你重选输入方式；若试连明确报“空账号被拒”，账号为必填（不再提供「留空（使用空账号）」选项），避免把同一个必失败的配置再存回去。**连接测试失败先读提示的末尾**：它给的是 dbhub 输出的尾部，并会说明失败发生在哪一层；配了隧道时再点「测试 SSH 隧道」就能把 SSH 层单独证明一遍——**报数据库层的错误就等于隧道已经通了**。诊断里的连接串一律清洗成 `mysql://****:****@host:3306/db`——**用户名和密码都不会出现**。
- **启用 / 禁用开关** — 关闭后所有 dbhub 工具立即返回「插件已禁用」友好提示，**侧边栏快捷入口同时隐藏**（禁用中的插件一律不贡献入口，与「在侧边栏显示入口」开关怎么设无关）；设置页与插件页那行的「配置」始终可进入，随时能再启用（不会自锁），无需重启。注意**隐藏入口 ≠ 禁用插件**：只想让左侧栏干净一点，就关掉设置条里的「在侧边栏显示入口」——插件照常工作、模型照常能查。
- **浏览器配置页** — 三个入口同一个页面：**设置 → DBHub 数据库工具**（一级设置页，推荐）、**左侧栏「DBHub 数据库工具」快捷入口**（插件已启用**且**「在侧边栏显示入口」开关为开时显示：关掉开关只是隐藏入口、插件照常工作，禁用插件则一律隐藏；设置页与插件页仍可进入并重新启用）、插件页 dsh-dbhub-live 那行的「配置」。实时展示状态徽章、工具数与环境数，并提供启用/禁用开关、连接增删改查、**环境改名**与连接测试。**连接列表按工作区组织**：所有工作区都只有一个环境时用平铺卡片（最多 3 列，一眼看全）；任一工作区有多个环境时按工作区分组折叠，**点组头展开/收起**，默认展开你最近使用的那个工作区，另有「全部展开/折叠」。每个连接**只占一行**（环境 · 🔒 类型/主机/端口/**库名** · source 句柄 · 图标操作）：窄窗口下会先截断主机/端口，**库名始终可见**；行内操作是 ⚡ 测试 / ✏ 修改 / 🗑 删除 三个小图标，不再用文字按钮占半行；`source` 句柄做成一个虚线小片（显示 `…` + 尾段，如 `…1a2b3c`），点它即复制、悬浮看全文（它就是让模型定位这条连接的句柄，不是复制整行连接串）。连接「来源」（手填 / 扫描 / 复制 / 自动发现）不占行宽，悬浮在环境名上即可看到（自动发现且未保存的会明确标出）。每个环境还能单独**开启只读**或配置**手动 SSH 隧道**（详见「只读模式与 SSH 隧道」一节）。自动更新间隔与「在侧边栏显示入口」开关一起收进「⚙ 设置」条，添加连接也默认收起（分组头右上角「＋ 环境」可直接在该工作区新增，工作区自动带入）。配色全部走 DSH 主题令牌，**跟随主题/皮肤与深色模式，包括半透明背景的主题**。写入前会拦截覆盖：**同名环境保存前先问「是否覆盖」**（取消则一个字都不写、表单原样留着让你改名），把环境改名落到已存在的环境时同样会问。
- **开箱即用** — 未安装 `dbhub` 时首次执行自动安装，之后按设置间隔自动更新。

## 支持的数据源

MySQL · PostgreSQL · MariaDB · SQLite · SQL Server

## 环境要求

- DeepSeek Harness 的 `dsh` CLI（`dsh web` 负责 GUI 运行）
- 兼容 **dsh 0.1.5 起的所有版本线**（含 0.2.x）：配置页在 0.1.x 走设置命名空间、在 0.1.7+/0.2.x 走插件自带的鉴权 HTTP 桥（`/api/dsh-dbhub-live/*`），两条通道展示同一份状态
- 推荐本机有 Node.js ≥ 18（含 `npm`）——首次执行会自动安装 `dbhub`
- **只读模式与 SSH 隧道需要 dbhub 1.4.0 及以上**：插件会自动检测版本，不满足时明确报错并给出升级指引（插件自动安装的版本满足要求）

## 安装

```bash
# 方式一：使用本机已安装的 dsh
dsh plugin --profile web add dsh-dbhub-live

# 方式二：通过 npx 调用 dsh（无需本机全局安装 dsh）
npx @deepseek-ai/dsh plugin --profile web add dsh-dbhub-live

# 更新到指定版本（推荐写明当前发布的版本号，避免 pnpm 判「Already up to date」跳过）
dsh plugin --profile web update dsh-dbhub-live@5.0.0
```

安装后**重启 `dsh web`** 生效（重启后到 **设置 → DBHub 数据库工具** 可看到配置页）。

> 从 4.x 升级：dsh 0.2.x 删除了旧版配置页依赖的 settings 命名空间接口，4.x 在 0.2.x 上会被 dsh 拒绝加载。5.0.0 起同时支持新旧两条 dsh 版本线，升级插件后配置页与既有连接、既有选项都会保留。

## 快速开始

以下工具由 DSH 的 AI 自动调用，你不用手动执行——直接用自然语言提出需求即可（如「查一下 users 表」）：

```text
# 1) 若当前工作区还没有连接，AI 先引导配置（密码在界面输入，AI 看不到）
dbhub_configure

# 2) 在已配置工作区的连接上执行查询（source 见 dbhub_list_sources）
dbhub_execute_sql  source=myapp  sql="SELECT * FROM users LIMIT 10;"

# 3) 查看已注册的连接与 source 值
dbhub_list_sources
```

## 工具

| 工具 | 说明 |
| --- | --- |
| `dbhub_configure(workspace?, env?, renameFrom?, copyFrom?, type?, host?, port?, database?, user?, readOnly?, sshHost?, sshPort?, sshUser?, sshAuthKind?, sshKeyPath?, sshProxyJump?, sshOff?)` | 为工作区配置/持久化数据库连接。**不接受 dsn 参数**——密码/连接串一律在界面输入（不经过模型）；type/host/port/database/user 可作为非敏感预填。**预填够用时插件会先自动试连**：可连通 → 直接保存并返回 source 值；提示要密码 → 弹出最小「账号（未知时）+ 密码」输入框；信息不全或其它失败 → 才弹出完整方式选择。**改名**：`env=新名` + `renameFrom=旧名`（连接与凭据原样保留，可用于 `default` → `prod` 或中英文互改；目标已存在时先请用户确认）。**跨工作区复制**：`copyFrom=其他工作区的 source 值` + `env=本工作区环境名`，插件在宿主侧复制连接，密码不经模型。**环境选项**：`readOnly:true` 为该环境开启只读（`readOnly:false` 会被拒绝——关闭只读只能由用户在配置页操作）；SSH 隧道用 `sshHost`/`sshPort`/`sshUser`/`sshAuthKind`（`key` 或 `password`）/`sshKeyPath`/`sshProxyJump` 配置，**SSH 密码与密钥口令只能由用户在弹窗里输入**（绝不接受模型传入），`sshOff:true` 解除隧道并保留连接与只读。 |
| `dbhub_list_sources()` | 列出全部连接源，**按工作区分组**并标出【当前工作区】：仅元数据（类型/主机/端口/库）+ 来源徽章 + 对应 **source 值**。 |
| `dbhub_execute_sql(source, sql)` | 在指定数据源上执行 SQL；`source` 见 `dbhub_list_sources`。**每个 source 只属于一个工作区**，优先用当前工作区的；要复用其他工作区的连接，先用 `dbhub_configure` 的 `copyFrom` 复制到当前工作区，不要直接拿别的工作区的 source 查询。每次调用为独立一次性连接，多语句用 `;` 分隔。 |
| `dbhub_search_objects(source, object_type, ...)` | 在指定数据源搜索数据库对象（表/视图/列/索引等）。 |

> **安全**：模型无法通过本插件拿到任何密码——结果与列表只标注 `mysql://host:3306/db` 这类元数据；dbhub 的报错文本在返回前也会被清洗。查询失败时按提示到界面更新密码即可。

> 注：`search_objects` 仅对 SQLite 开放；MySQL / PostgreSQL 等请用 `dbhub_execute_sql` 直接查（如 `SHOW TABLES`）。

### 配置方式

0. **自动试连（默认优先）** — 你在对话里说出连接信息（如「mysql 198.51.100.1:3307/mydb」）后，插件先用这些非敏感信息实测：能连上就直接保存（数据库不需要密码时全程零输入）；提示需要密码 → 弹窗只问「账号（未知时）+ 密码」，其余信息自动沿用，并附失败原因与该连接信息不对时的「改用其他方式」入口；若试连明确报“空账号被拒”（如 `Access denied for user ''`），账号为必填（不提供「留空」选项）；信息不完整或其它原因失败，才进入下面三种方式。若你说的是另一个库/主机/端口（与已存连接不同），插件会按新信息重新试连判断。
1. **显式 DSN** — 在界面输入完整连接串，如 `mysql://user:pass@host:3306/db`。
2. **填写分项** — 在界面按类型 / 主机 / 端口 / 账号 / 密码 / 库名依次填写；已从对话中得知的字段会自动带入，只补缺项即可。
3. **授权扫描** — 授权后扫描项目配置文件（`.env`、`application*.yml`、`docker-compose`、`jdbc.properties` 等），列出候选（只显示主机/端口/库，密码不显示，由插件直接读取）供你确认。

工作区若已有 `mise env` 或 `.env`（`DSN` / `DB_*`），插件会自动发现，无需手动配置。

## 配置页

三个入口，同一个页面、同一份状态：

1. **设置 → DBHub 数据库工具**（推荐）：插件在设置面板注册的一级页面，任何部署都有。
2. **左侧栏「DBHub 数据库工具」**：快捷入口，**当插件已启用、且设置条里的「在侧边栏显示入口」开关打开时显示**（开关默认开启，随时可改、即刻生效，无需重启）。**隐藏快捷入口不等于禁用插件**：关掉开关后入口消失，但插件继续工作、模型照常可以查询；想整体停用插件才用页面顶部的「禁用」——禁用后入口一律隐藏。
3. **插件 → dsh-dbhub-live → 配置**：dsh 0.1.6 起官方「插件」页给每个插件行提供的配置控件（该页由官方插件管理器提供，缺失时用前两个入口）。

> 侧边栏入口消失（关掉了开关，或插件被禁用）**不会**让你失去配置页：设置页与插件页那行的「配置」始终可用，随时能重新打开开关或启用插件。

配置页全部文案（名称、状态、配置项、按钮、连接行）跟随 dsh 界面语言（中 / 英，设置 → 通用 → 语言）切换；模型的报错/反馈与宿主日志同样跟随。

**状态**：状态徽章（🟢 运行中 / ⚪ 已禁用）、**启用/禁用开关**、工作模式（一次性连接）、工具声明（`4 个（固定）`）、环境数（`N 个 · 已保存 M`）、最近错误（异常时红色展示）。

**配置**（编辑后点「保存配置」即时生效并持久化）：

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| 自动更新间隔(天) | 自动更新 dbhub 的间隔天数，`0` 关闭 | `7` |
| 在侧边栏显示入口 | 是否在左侧栏显示本插件的快捷入口；关闭只隐藏入口，插件继续工作（工具照常可用），**并非禁用插件** | 开启 |

侧边栏入口的显示条件是**两者同时成立**：插件已启用，**且**「在侧边栏显示入口」为开。**隐藏快捷入口不是禁用插件**——关掉开关后入口消失，但插件仍在工作、模型照常可以查询；禁用插件则一律不显示入口（禁用中的插件不贡献任何侧边栏入口）。删掉入口也删不掉退路：设置页与插件页那行的「配置」始终可进入，两种状态都能在那里撤销。

优先级：**配置页保存的设置 > 进程环境变量（默认值种子）> 内置默认**；从 0.1.x 老版本升级时，原先存在设置文档里的选项会被读进来作为更低一层（不会被静默重置）。在 dsh 0.1.7 及以后，「自动更新间隔」与「在侧边栏显示入口」同时是本插件的声明式配置（volatile Config：`updateIntervalDays` / `showSidebarEntry`）：也可以直接写进 `cordis.patch.yml` 的该插件行，或在官方「插件」页的表单里改——**任一处改动都会被采纳，本插件配置页会显示同一个值**（配置页保存也会同步写回该配置，两边不会打架）。自动安装包不在 UI 中（`DSH_DBHUB_PACKAGE` 环境变量单独控制，默认 `@bytebase/dbhub`）。

**工作区连接**：

- 列出每个工作区 × 环境的连接：工作区名、环境名、**source 值**（模型调用 `dbhub_execute_sql` 时填这个，等宽字体显示）、**连接元数据**（🔒 `mysql://host:3306/db`——不含账号密码，密码永不出现在页面上）、来源徽章（`已保存` / `自动`）与来源明细（`已保存·用户` / `已保存·扫描` / `已保存·复制` / `自动·mise env` / `自动·.env`）。
  - `已保存`：你配置过（`dbhub_configure` 或配置页添加）。
  - `自动`：未保存，来自 `mise env` / `.env` 自动发现——不持久化，随源文件变化；自动发现不对时可直接「修改」为手动配置覆盖。若你对这类环境**显式设置选项**（只读 / SSH），插件会把它**提升为已保存连接**（按当前发现到的连接串落库）并明确提示，此后它不再随源文件变化。
- 每行可「测试」（连接探活，见下）、「修改」（改连接串 **或改环境名**；改名连接与凭据原样保留，只填名字不填连接串即为纯改名）或「删除」（仅已保存项）。
- **连接测试**：点「测试」后 Host 用该环境**真正会被使用的有效连接**走一次性临时连接（独立 dbhub 进程执行 `SELECT 1`）实测可达性——已开启只读、配置了 SSH 隧道时，测的就是"经隧道 + 只读"的那套组合；测试中显示已耗时（`测试中… 1.2s`），成功 / 失败即时在行内提示。结果是一次性反馈：不持久化、约 10 秒后自动消失；失败不会标记、限制或改动这条连接，不影响其他环境与查询。测试**不会**为了拿连接串而重扫所有工作区（已保存的环境直读本地凭据、自动发现的环境用列表上那一行，只有从未扫描到的环境才做一次真实发现），因此点「测试」的耗时≈探测本身。等待上限：直连约 25 秒、经 SSH 隧道约 45 秒（界面兜底 30 秒 / 60 秒），超时会给出明确提示而不是一直等待。**失败时看提示的末尾**：诊断给的是 dbhub 输出的**尾部**（多行、约 600 字符、保留换行，**按行边界截断**并丢掉 `at …` 之类的栈帧残片，所以消息不会以半行开头）——致命的那一行就在末尾，只截开头会把真正的错误漏掉。配置了隧道时，提示还会**标出失败发生在哪一层**：「【SSH 层】隧道未建立：…」或「【数据库层】隧道可能已建立，失败发生在数据库连接/认证：…」（后者只能说"可能"——只有「测试 SSH 隧道」才能证明隧道真的起来了，见下）。**读法很直接：报【数据库层】就说明隧道这一层已经通了**——错误来自隧道后面的数据库（认证 / 库名 / 目标地址），不必再怀疑 SSH；想把"可能"钉成确定结论，点一次「测试 SSH 隧道」。插件自身无法启动 dbhub 或生成配置时另有「【插件层】…」前缀，那既不是隧道层也不是数据库层。提示里的连接串一律清洗成 `mysql://****:****@host:3306/db`：**用户名和密码都不会出现**。
- **同一工作区可添加多个环境**：表单填「工作区（路径或标题，留空=默认当前工作区）+ 环境名 + 连接串」点「添加连接」。环境名**支持中文**（如 `线上` / `测试`）：显示用原名，source 值中的环境段用 `env-<短哈希>` 保证**不同中文名不会撞车**（纯 ASCII 名如 `test` / `dev` 的 source 值保持不变）。

## 🔒 只读模式与 SSH 隧道

这两项都是**按环境（工作区 × 环境）**设置的连接选项，由 dbhub 原生能力执行。开启只读或隧道后，该环境的每次执行都会改用一份**临时生成的 dbhub 配置**——文件里只有 `${…}` 占位符、**不含任何密码**（真值只经子进程环境传入），用完即删；其余环境与以前完全一致。

### 只读模式

- **怎么开**：在连接行点 ✏ 修改（或在「＋ 添加连接」表单里）勾选「只读模式」后保存；模型也可以为某个环境开启只读。**关闭只读只能由你在配置页操作**——模型可以开、不能关（否则等于自行解除你设的限制），模型尝试关闭会被拒绝并提示你到配置页处理。
- **开启后会被拒什么**：dbhub 只放行只读语句（`select` / `with` / `explain` / `pragma` 等，随数据库类型不同），写操作（`INSERT` / `UPDATE` / `DELETE` / DDL 等）由 dbhub 直接拒绝并返回 `READONLY_VIOLATION`；模型看到的是这个原始错误加上一句中文引导。对象搜索（`dbhub_search_objects`）在只读环境下**照常可用**。
- **怎么认出来**：只读环境的环境名后面会多一个「只读」小标（英文界面为 `RO`），悬浮还有说明。
- **注意**：只读是**逐环境**开关，没有"全部环境只读"的全局开关；要整体停用插件请用「禁用」。

### SSH 隧道（手动配置）

适用于「数据库只在跳板机后面、必须经 SSH 才能连」的场景。字段：

| 字段 | 说明 |
| --- | --- |
| SSH 主机 | **域名或 IP**（如 `203.0.113.10`）。不要填 `~/.ssh/config` 里的别名——不带点号的裸名字会被 dbhub 当作别名去解析，本插件不支持这种用法。 |
| 端口 | 默认 `22`。 |
| SSH 用户 | 登录跳板机使用的账号。 |
| 认证方式 | **密钥**（填密钥路径，如 `~/.ssh/id_ed25519`；私钥有口令时可再填口令；**密钥路径留空 = 用默认 `~/.ssh/id_ed25519`**）或**密码**。 |
| ProxyJump | 可选，**只支持一跳**，格式 `[user@]host[:port]`（如 `203.0.113.11:22`）。 |
| 密钥口令 / SSH 密码 | **只能在界面输入**，不经模型、也不回显；编辑时**留空 = 保持原值**。 |

> **密钥路径留空 = 用默认身份文件**：认证方式选「密钥」而「密钥路径」留空时，插件按 SSH 客户端的惯例取 **`~/.ssh/id_ed25519`**（正是该字段占位符显示的那个值）。这条默认**只作用于「密钥认证 + 路径为空」**：字段里填了路径就绝不覆盖，密码认证完全不受影响；**保存与测试走同一条规则**（否则会出现"测试通过、保存却把隧道悄悄丢掉"）。秘密字段的**「留空 = 保持原值」不变**：密钥口令 / SSH 密码留空照旧沿用已存值，已存的密钥路径在字段留空时也照旧保留（此时不会套用默认）。「测试 SSH 隧道」的结论会**写明这次实际用的路径**（"未填密钥路径，已按默认 `~/.ssh/id_ed25519` 尝试；想用别的密钥请在该字段里填写路径。"），省得你去猜是不是少打了一个字符。**诚实边界**：默认文件在你那台机器上可能并不存在——探测会直接给出可执行的答案 `SSH 密钥文件不存在或不可读：~/.ssh/id_ed25519`（同样带上面那句说明），而不是含糊的"配置不完整"。

「高级：SSH 隧道」里有**两个**测试按钮：「**测试 SSH 隧道**」只验证**隧道这一层**（主机/端口能否从本机连通、私钥文件在不在、SSH 握手与认证能否起来），「**测试该配置**」则按"隧道 + 只读"的**有效连接**实测。先点前者，就能立刻把"隧道问题"和"数据库问题"分开。**关键一点：数据库层的错误就是隧道已经通了的证据**（判定顺序与特征见下面第 5 条）。

前提与限制：

- 需要 **dbhub 1.4.0 及以上**：版本过旧时插件会明确报错并给出升级指引，**不会**静默忽略隧道或只读设置。
- **连接串里的数据库地址必须是"从跳板机看过去"的地址**：例如数据库就在跳板机本机时写 `mysql://user:CHANGE_ME@127.0.0.1:3306/db`，而不是你本机视角的地址。
- **多跳跳板机、`ProxyCommand`、ssh-agent 不支持**（dbhub 的多跳共用同一份登录凭据，无法表达各跳不同的认证信息）；命中时插件会明确报"不支持多跳"并给出指引，只支持一跳。
- 插件**不复用也不读取**任何其他插件（包括 DSH 自带的 SSH 工具）的 SSH 配置：隧道信息只来自你在这里手动填写的内容。
- 只读与 SSH 是两个独立开关，可以只开其中一个。

### 隧道连不上怎么排查

1. 确认**跳板机本身可达**：在本机 `ssh 用户@203.0.113.10` 能登录。
2. 确认**连接串里的主机/端口是跳板机能访问到的地址**——这是最常见的原因（填了本机视角的地址；库就在跳板机本机时应写 `127.0.0.1`）。
3. 确认**密钥路径存在且可读**（`~` 会被展开；字段留空时用的是默认 `~/.ssh/id_ed25519`，探测会报出它是否存在）；加密私钥记得填口令。
4. 确认**只有一跳**：ProxyJump 里写多个（逗号分隔）会被拒绝。
5. 先点**「测试 SSH 隧道」**把隧道层单独验一遍。它只测 SSH 层，依次给你三个答案：① 先做 `ssh_host:ssh_port` 的 **TCP 可达性**探测（约 5 秒预算），失败会直接说「主机不可达 / 端口未开放」并带上**套接字错误码**（`ENOTFOUND` 域名解析不了 / `ECONNREFUSED` 端口没有服务 / `ETIMEDOUT` 被防火墙丢包）——这一步单独就能把 DNS、防火墙、端口问题摘出去；② 密钥认证时会检查**私钥文件存在且可读**（`~` 会展开）；③ 最后**故意**让 dbhub 对一个不可能在监听的地址（`127.0.0.1:1`）建隧道，再按证据判定，顺序固定：**SSH 自身特征**（认证方式都不通、私钥无法解析、加密私钥缺口令、握手或 ProxyJump 问题）**单独就足以判定隧道这一层断**（这类特征只会由隧道级问题产生）；否则**数据库层特征**（`PROTOCOL_CONNECTION_LOST`、`Connection lost`、`server closed the connection`、`Access denied`、`Unknown database`、`ER_*`、`ECONNREFUSED` / `ECONNRESET` / `ETIMEDOUT` / `EHOSTUNREACH`、`SSH tunnel closed`）**证明连接已经穿过了隧道**——驱动只有等到转发连接建立之后才会说话，所以结论是「SSH 隧道可用」；否则如果报错**指名了转发目标**，同样算隧道可用；两者都没有时才如实给「SSH 层结果无法判定」并附上输出末尾，不猜。**一句话记住：数据库层（含 `SSH tunnel closed` + `Connection lost`）的报错 = 隧道是好的，问题在隧道后面的数据库。** **它的边界也要知道**：这证明的是"网络通 + 密钥在 + SSH 层起得来"，**不是**一次带真实数据库的完整 SSH 会话测试——隧道建起来不等于隧道后面的库一定连得上，那一步仍由「测试该配置」回答。
6. 保存前再点「测试该配置」：它按"隧道 + 只读"的**有效连接**实测（隧道首次握手较慢，最长约 45 秒），失败会带出原因——**读提示的末尾**，它给的是 dbhub 输出的**尾部**（约 600 字符、保留换行，**按行边界截断**并丢掉 `at …` 之类的栈帧残片，所以消息不会从半行开始）；它还会说明失败发生在 SSH 层还是数据库层——**报【数据库层】就说明隧道这一层已经通了**。

## dbhub 环境变量

| 环境变量 | 说明 | 默认 |
| --- | --- | --- |
| `DSH_DBHUB_PACKAGE` | 自动安装使用的 npm 包名（仅环境变量，不在 UI 暴露） | `@bytebase/dbhub` |
| `DSH_DBHUB_UPDATE_DAYS` | 自动更新间隔天数种子，`0` 关闭（被设置卡片保存过的值覆盖） | `7` |

## 🔄 dbhub 自动安装与更新

- **首次使用自动安装**：本机没有 `dbhub` 时，插件会在第一次执行时自动安装，之后离线也可用。
- **自动保持更新**：后台静默更新到最新版（间隔见「配置页 → 可配置参数」），失败则沿用现有版本。
- **不碰你的配置**：通过 PATH / mise 自行安装的 `dbhub` 不会被插件改动。

> 更新间隔默认值也可用环境变量播种，见「配置页 → 配置」；一旦在设置卡片保存过，即以设置值为准。

## 数据位置

所有配置与凭据存放在模块目录之外（不受 pnpm 打包影响），删除该目录即可完整清空：

```
~/.dsh/storages/dsh-dbhub-live/
```

按 `DSH_HOME` 实例隔离，同一实例的多个 profile 共享（与 dsh 自身 `workspace.json` 同一约定）。工作区连接按「工作区 × 环境」存储（`environments.default` 为默认环境）；v1 旧格式单连接条目启动时自动迁移。插件对升级/手改遗留的旧格式配置自动清洗并一次性迁移；运行目录被误删或写入被系统拦截时不会崩溃——自动重建目录、写入失败仅告警并继续内存态运行。**没有常驻 dbhub 进程与共享配置文件**：同机多实例、同 DSH_HOME 并发运行也不会互相干扰。开启只读 / SSH 隧道后，每次调用会在 `tmp/` 下临时生成一份 dbhub 配置——**文件里只有占位符、不含任何密码**，用完即删；崩溃残留会在下次启动时自动清理。

## 故障排查

| 现象 | 处理 |
| --- | --- |
| 首次使用报「无法获取 dbhub」 | 确认本机有 npm 且能联网；离线可手动安装 `dbhub` 并加入 PATH。 |
| 某个环境的查询报连接被拒 / 认证失败 | 该环境为独立一次性连接：不可达只让该次调用报错，其他环境与调用不受影响。错误末尾会附指引——凭据或连接信息有误时，可让 AI 调用 `dbhub_configure` 引导你在界面更新，或直接在 插件 → dsh-dbhub-live → 配置 中修改。 |
| 工具显示「插件已禁用」 | 打开 插件 → dsh-dbhub-live → 配置，点击「启用」。 |
| 禁用后左侧栏入口不见了 | 这是预期行为：禁用中的插件一律不贡献侧边栏入口。到 **设置 → DBHub 数据库工具**（或 插件 → dsh-dbhub-live → 配置）点「启用」，入口立即回来。 |
| 关掉了「在侧边栏显示入口」，工具还能用吗 | 能。关开关只隐藏快捷入口，插件继续工作、模型照常可以查询（这正是「隐藏入口」与「禁用插件」的区别）。想恢复入口就在设置条里重新打开它。 |
| 开启只读后写操作报 `READONLY_VIOLATION` | 这不是故障，而是只读模式正在生效（由 dbhub 直接拒绝）。需要写入时，在配置页取消该环境的「只读模式」——模型无法关闭它。 |
| 只读 / SSH 控件是灰的，或提示 dbhub 版本过旧 | 这两项需要 dbhub 1.4.0+。升级 dbhub，或删除 `~/.dsh/storages/dsh-dbhub-live` 让插件自动安装一个满足要求的版本。 |
| 连接测试失败，但看不出原因 | 读提示的**末尾**：它给的是 dbhub 输出的尾部（多行、约 600 字符、保留换行、按行边界截断），配置了隧道时还会标出失败层（【SSH 层】/【数据库层】）。**报【数据库层】就说明隧道这一层已经通了**——错误来自隧道后面的数据库（认证 / 库名 / 目标地址），不用再怀疑 SSH；想把这一点钉成确定结论，点「测试 SSH 隧道」。有隧道时先点它独立验证 SSH 层，再按下面那条排查。 |
| SSH 隧道连不上 | 先点**「测试 SSH 隧道」**把隧道层单独验一遍（它会分别告诉你端口通不通、私钥在不在、SSH 认证起没起来）。**结论按证据给，不猜**：报错里带 SSH 自身特征（握手 / 认证 / 私钥）才是隧道断；带**数据库层特征**（`PROTOCOL_CONNECTION_LOST`、`Connection lost`、`server closed the connection`、`Access denied`、`Unknown database`、`ER_*`、`ECONNREFUSED` / `ECONNRESET` / `ETIMEDOUT` / `EHOSTUNREACH`、`SSH tunnel closed`）或指名了转发目标，都说明连接**已经穿过隧道**，结论是「SSH 隧道可用」——问题在隧道后面的数据库；两者都没有时才如实说「SSH 层结果无法判定」并附输出末尾。再依次检查：跳板机可达 → 连接串里的地址是"跳板机看过去的地址"（库在跳板机本机时用 `127.0.0.1`）→ 密钥路径存在且可读（留空则用默认 `~/.ssh/id_ed25519`）→ ProxyJump 只有一跳。详见「只读模式与 SSH 隧道 → 隧道连不上怎么排查」。 |
| 看不到配置页 | 确认插件已安装并重启 `dsh web`；配置页只在 Web 设置面板（`dsh web`）显示，在无设置面板的终端环境下不影响工具使用。 |
| 升级 dsh 后提示插件与本版 dsh 不兼容 | 这是 dsh 的 peer 版本检查：升级插件到 5.0.0 及以上（同时支持 0.1.x 与 0.2.x）。用 `dsh plugin --profile web allow-version` 强行豁免没有意义——4.x 依赖的接口在 0.2.x 已被删除，加载后配置页依然是空的。 |
| 扫描不到配置文件 | 默认跳过 `node_modules` / `.git` / `target` / `dist` 等目录，可改用「输入 DSN」或「填写分项」。 |
| 需要自定义 dbhub 版本 | 设置环境变量 `DSH_DBHUB_PACKAGE`（如 `@bytebase/dbhub@1.4.0`；只读 / SSH 隧道需要 1.4.0+）后重启；或删除 `~/.dsh/storages/dsh-dbhub-live` 重新自动安装。 |
| 不希望自动更新 dbhub | 配置页「自动更新间隔(天)」填 `0` 并保存；或设置环境变量 `DSH_DBHUB_UPDATE_DAYS=0`。 |
| 密码无法在对话中更新（模型问你要密码） | 这是设计如此：模型不应接触密码。让 AI 调用 `dbhub_configure`，在界面弹出的输入框中填密码即可；或自行到 插件 → dsh-dbhub-live → 配置 修改。 |
