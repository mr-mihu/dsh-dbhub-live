# dsh-dbhub-live 需求事实记录

> 本文只记录「产品必须满足什么」的**需求事实**（概念层面），不含实现细节；开发实现说明见 `AGENTS.md`，用户安装使用见 `README.md`。
> 版本基线：5.1（正式版；在 5.0 的零知识凭据 + 一次性进程执行 + dsh 双栈配置页之上，新增环境级只读、手动 SSH 隧道、侧边栏入口开关（与启用状态取交集）、SSH 层独立连通性测试、连接测试分层诊断，以及连接测试快路径）。
> 当前迭代：5.1 — 环境级只读 + 手动 SSH 隧道 + 侧边栏入口开关 + SSH 层独立连通性测试 + 连接测试分层诊断与性能（见第十节 R43/R44/R56-R58、第十一节 R49 与第十二节 R59-R65）。

## 一、产品定位

- R1. 插件为 DSH 提供数据库查询、对象搜索与连接管理能力。
- R2. 连接配置是长期资产，被维护与复用；每一次数据库执行是一次性的、相互独立的劳务行为。

## 二、凭据零知识（安全红线）

- R3. 密码、用户名与完整连接串（DSN）不得出现在模型上下文中的任何位置：工具参数、工具描述、查询结果、错误文本、来源列表均不得包含。
- R4. 模型仅凭「工作区/环境标识（source）」与元数据（数据库类型、主机、端口、库名）完成定位与执行，由插件在宿主侧解析真实凭据并自行执行。
- R5. 凭据的录入与修改必须由人在界面完成（或经授权后由插件仅在本机读取，如项目文件扫描），不得经模型转述。
- R6. 查询因鉴权/连接失败时，系统应给出「凭据或连接信息可能有误」的明确指引，引导用户在界面更新，而非要求模型提供密码。
- R7. 任何底层工具返回的文本在呈现给模型之前必须经过清洗，防止异常路径泄漏密码。

## 三、连接管理

- R8. 支持按工作区配置专属连接，一次配置长期复用。
- R9. 同一工作区可配置多个环境（默认环境与命名环境），彼此独立、可区分、不混淆。
- R10. 连接录入支持三种方式：直接输入连接串、按分项填写、授权扫描项目配置文件后确认；扫描敏感文件必须先经用户授权。
- R11. 工作区已有自动配置（mise env / .env）时可自动识别连接、免手工配置；自动识别项不被持久化。
- R12. 用户可在设置界面查看、新增、修改、删除连接，并可测试连接可达性；测试结果不持久化、仅即时反馈。

## 四、查询与对象搜索

- R13. 模型可通过来源标识执行 SQL，以及搜索数据库对象（表、视图、列、索引等）。
- R14. 支持以分号分隔的多语句 SQL。
- R15. 工具声明数量恒定，不随连接（工作区 × 环境）数量增长。

## 五、执行与运行保障

- R16. 每次执行独立、一次性，不共享长期进程状态；单次执行失败不影响其他执行。
- R17. 支持多任务并发执行，互不影响。
- R18. 支持多个 DSH 实例并存运行，互不影响、无冲突。
- R19. 首次执行缺少依赖时自动安装 dbhub，并按设定间隔自动更新；用户自装版本不受影响。
- R20. 插件可启用/禁用；禁用后所有工具应立即返回友好提示。

## 六、设置与状态界面

- R21. 浏览器端提供配置页：展示启用状态、工具声明数、环境数、最近错误（工作模式作为状态行提示），并支持启用/禁用开关、连接的增删改查、环境改名与连接测试。在 dsh 0.1.6 及以后，该配置页承载于官方「插件」页的插件行上（`plugins.row.config`），不再是设置面板里的独立卡片。
- R22. 面板文案与模型侧反馈跟随 DSH 界面语言（中/英）。

## 七、存储与实例隔离

- R23. 配置与凭据仅存本机用户目录，按实例（DSH_HOME）隔离；共享同一主目录的并发实例写入互不破坏（不产生半写文件）。
- R24. 配置持久化失败不应导致崩溃，可降级继续运行。
- R25. 升级或手工修改遗留的旧格式配置应被自动清洗/迁移，未知字段予以保留。

## 八、连接配置交互原则（零打扰优先）

> 本节由 4.0.x 交互优化迭代（探连优先 + 凭据最小询问）沉淀，覆盖用户侧三轮反馈：①可用直接可用、缺什么问什么；②已存连接凭据缺失时应诊断并只补缺失项；③连接信息本身不对或重新描述了目标时应能脱身并按新信息重走判断。

- R26. 对**已配置且校验可用的连接**，配置过程必须自动校验；通过时直接确认「已配置可连通」并提供使用指引，**不要求用户重新输入任何信息**。
- R27. 仅当环境未配置、校验失败或自动试连未成功时才向用户提问；**提问不得索要已知或重复信息**——完整连接串已含密码时，不得再次索取密码。
- R28. 未配置环境下，若已从对话中得知足够的连接事实（类型/主机/库名；SQLite 除外），应**先自动试连**、按结果分流，而不是直接提问：
  - 试连成功 → 按已有信息完成配置并返回可用来源标识，**全程零输入**（免密码连接、信息即用即存）；
  - 试连提示缺凭据 → **只询问缺失项**（账号未知时连账号一起问），其余信息自动沿用，补完即生效；
  - 信息不完整或试连因其它原因失败 → 才提供完整录入方式（输入连接串 / 分项填写 / 授权扫描）。
- R29. 凭据询问必须**说明为什么需要**（试连失败原因），并允许用户表明「连接信息本身不对」从而改走完整录入，避免用户被困在反复补凭据的循环中。**若试连诊断明确指向“空账号被拒”（如 `Access denied for user ''@…`），账号为必填**：凭据询问不得提供「留空（使用空账号）」选择，用户仍提交空账号时应拒绝保存并说明原因，避免把同一个必失败的 DSN 再存回去。
- R30. 用户重新描述的目标（库/主机/端口等）与已存连接不同时，必须**按新描述重新执行判断流程**，不得沿用旧连接的结果。
- R31. 「使用现有连接」是**字面沿用**：不修改、不补填任何缺失字段（如账号/密码）；其文案必须让用户明确这一点，不得暗示会修复缺失项。
- R32. 录入表单与凭据询问都应**预先带入已从对话中得知的字段**，用户只需补充缺失项，避免重复录入。
- R33. 连接保存或被采纳后，应**立即自检连通性**并把结果（可连通 / 失败原因）随回执一并返回，避免用户通过后续尝试才得知失败。
- R34. 连接信息输入界面只提供一个取消入口（由界面自身提供），不得出现重复取消项。

## 九、工作区隔离与来源解析

> 本节由 4.1 迭代沉淀：多工作区各自配置了相似（甚至同名）连接时，模型必须能分辨「这是哪个工作区的哪个环境」，不允许把不同工作区的连接当成同一个使用。

- R35. 每条连接只属于一个工作区；不同工作区的连接是彼此独立的目标，即使连接信息看起来相同也不得视为同一条（不共享、不互相覆盖、不互相替代）。
- R36. 模型侧应优先使用**当前会话工作区**的连接；连接清单必须按工作区分组并显式标出当前工作区。
- R37. 当模型给出的来源标识可能命中多个工作区（同名工作区、同名环境或仅给标题）时，系统必须返回候选清单要求明确指定，**不得按列表顺序或长度猜测**。
- R38. 需要复用其他工作区已配置的连接时，必须先取得用户确认，再由插件在宿主侧把连接**复制**到当前工作区（新建一条属于当前工作区的连接）；凭据与连接串不得因此进入模型上下文，也不得直接用其他工作区的来源标识执行查询。
- R39. 环境名支持非 ASCII（如中文「线上」「测试」）：显示与存储保留原名，而用于来源标识的环境段必须**唯一且稳定**——不同中文环境名不得解析到同一个来源；纯 ASCII 名的既有来源标识保持不变。
- R40. 环境可改名（模型可调、界面可改）：改名只更换名字，连接与凭据原样保留、无需重新输入；目标名已存在时必须先经用户确认（该操作会覆盖目标环境的连接）。
- R41. 配置目标必须明确：显式给出的工作区不存在时应报错并列出可用工作区，不得静默改用其他工作区；未给出工作区时以当前会话工作区为准，无法确定时应要求明确指定。

## 十、配置页与桌面端承载（dsh 版本适配）

- R42. 配置页必须可通过**设置**进入：插件在设置面板注册一级页面（设置 → DBHub 数据库工具），该承载位属核心界面、任何部署都存在，用户也在此寻找连接管理；同时在官方「插件」页按当前 dsh 版本提供的单插件配置槽位（0.1.6 起为 `<包名>#<行 id>` 的配置页）再挂一份。三处进入的是同一个页面与同一份状态。
- R43. 插件另提供**侧边栏快捷入口**，其显示由**两个条件同时成立**决定：插件处于启用状态，**且**用户在设置条（设置 → DBHub 数据库工具 → ⚙ 设置）里打开了「在侧边栏显示入口」开关（默认开启，随其他选项持久化）。任一条件不成立即隐藏，改动即时生效、无需重启或刷新。
  - **「隐藏快捷入口」与「禁用插件」是两件事**：关掉开关只是不显示入口，插件继续工作、模型仍可正常使用工具；禁用插件则一律不显示入口——禁用中的插件不贡献任何侧边栏入口。
- R44. 侧边栏入口的显隐（无论是被上述开关关闭，还是因插件禁用而消失）**不得**造成自锁——设置页与插件页入口必须始终可用，用户必须能据此重新打开开关或启用插件；官方槽位变化或缺失（如 dsh 升级移除旧槽位）同样不得导致配置页不可达。
- R56. 插件必须同时支持两条 dsh 版本线（0.1.x 与 0.2.x）的配置页数据通道：dsh 升级删除插件所依赖的宿主接口时（如 0.1.7 起 settings 命名空间被 Config 表单取代、0.2.x 删除浏览器侧 `settingsScope` 服务），插件**不得**因等待一个永远不会出现的服务而静默失活（表现为配置页/侧边栏/插件页入口全部消失且无任何报错）。浏览器半必须主动探测可用通道并降级；页面数据与写入能力在两条通道上必须等价。
- R57. 新增通道不得削弱既有安全边界：浏览器↔宿主的状态读取只承载元数据（延续 R3/R4），连接串只在写入方向从浏览器直达宿主；写入路由必须与 dsh 自身的接口鉴权一致（未鉴权的请求必须被拒绝），不得因为"插件自有路由"而绕过鉴权。
- R58. 插件选项（自动更新间隔、**在侧边栏显示入口**）必须在两条版本线上都能持久化，并且升级插件不得静默重置用户已保存的值（旧版本的设置文档作为更低一层被读入）。在 0.1.7 及以后，这些项同时作为插件的声明式配置暴露（`updateIntervalDays` / `showSidebarEntry`）：可经 `cordis.patch.yml` 或官方插件表单设置，且**与插件自有配置页共享同一个有效值**——任一处的改动都必须在另一处立刻可见（不得出现"改了表单但页面不变"或反之）。侧边栏开关只决定入口显隐，不改变插件的启用状态（见 R43）。

## 十一、配置页布局与空间占用

> 本节由 4.2 迭代沉淀：连接数量增长后，原「每个连接三到四行 + 常显添加表单」的平铺列表把大量高度花在重复的工作区标题与固定块上；下列要求把列表改为按工作区组织、每连接一行。

- R45. 连接列表必须**按工作区组织**，并在两种呈现间自动选择：**所有工作区都恰好只有一个环境**时使用**平铺**（一格一个工作区，信息全露、无需展开）；**任一工作区有多个环境**时使用**按工作区分组**。判定只取决于"是否存在多环境工作区"，不引入数量阈值。
- R46. 工作区分组必须支持**点击组头展开/折叠**，组头显示该工作区的环境数与已保存数；分组以**工作区路径**为身份（同名工作区是不同目标，不得仅凭标题合并，同名时必须可见地消歧）。
- R47. 默认展开态：单个工作区自动展开；多工作区时展开**用户最近使用的工作区**，其余折叠；无法判定最近工作区时全部折叠。必须提供「全部展开 / 全部折叠」总控。用户的展开/折叠选择在同一次页面会话内保留（跨重挂载有效），**不跨刷新持久化**。
- R48. 列表中**每条连接只占一行**：环境名、连接元数据（类型/主机/端口/库名）与操作；`source` 句柄不得再单独占据整行，改为**可复制入口**（保持可复制性，且必须让人看得出复制的是 source 句柄而不是整行连接信息）。**库名必须始终可见**：窄行下可截断主机/端口前缀，不得把库名截掉。行内操作以图标承载（必须带 `title`/`aria-label` 说明），不得用文字按钮占掉行宽。**连接的「来源」（手填/扫描/复制/自动发现）不得作为行内徽章常显**——它对绝大多数行都一样，却会抢走行的视觉焦点；应改为按需查看（悬浮提示），其中「自动发现且未持久化」这一例外需明确提示（该条尚未保存）。列表内不得出现密码或完整 DSN（延续 R3）。
- R49. 低频内容必须收拢：状态与开关收成页面顶部一行，自动更新间隔与**「在侧边栏显示入口」开关**（默认开启）一起放进默认收起的设置条；**添加连接表单默认收起**。分组内新增连接必须自动带入该工作区（不要求用户重复填写/选择工作区）。关闭该开关只影响侧边栏入口的显隐（见 R43），不影响插件的启用状态与工具可用性。
- R50. 界面配色必须使用 DSH 主题令牌，随主题/皮肤与**半透明背景**自适应：样式表中不得出现不透明色字面量（含兜底值），正文与操作文案的对比度不得依赖固定浅灰。用户可能安装主题/皮肤插件覆盖或省略令牌，此时界面仍需可读（表面继承页面背景而不是涂上白块）。
- R51. 工作区分组与其环境行之间必须有**可见的层级区分**（缩进、引导线、边框或阴影等），不得让组头与环境行看起来是同一层。
- R52. 界面写入连接时，若目标工作区的目标环境名**已经存在**（新增落到已存在环境，或改名落到已存在环境），必须**先提示"将覆盖该连接"并要求用户确认**；取消则不得产生任何写入，并保留用户已填内容以便改名。判定必须使用与宿主一致的环境名规范化规则（去控制字符、trim、空值→`default`、限长），否则会出现"看起来不同、实际是同一个键"的漏判。仅修改**同一个环境**的连接不属此列（那正是编辑的目的，不需二次确认）。
- R53. 界面操作的**结果必须即时可见**：新增/删除/改名/连接测试提交后，列表不得等到"重新扫描全部工作区"才更新，也不得出现"先整块消失、稍后再出现"的空窗。理想顺序是：宿主应用写入后立刻按已知状态回推，再以权威扫描校正（扫描失败时保留最后一次可用列表）。
- R54. 从界面复制连接信息（连接串标签等）必须得到**可直接使用**的字符串：不得因为渲染分层（例如把类型/主机段与库名拆成两个盒子）而混入空格、换行等分隔符。
- R55. **连接发现不得被单个工作区拖死**：自动发现（mise env / .env）的每一次外部探测都必须在有限时间内返回（超时即放弃该工作区的自动发现，不影响其他工作区与已配置连接），且同一目录的结果在短时间内可复用（避免每次列表/执行都重新探测）。**界面显示连接与模型侧看到连接必须一致**：卡片写入所用的工作区标识必须与发现/查询所用的同一份注册表，不得出现"设置里有、模型列不出来"。

## 十二、环境选项与上游能力门槛

> 本节由 5.1 迭代沉淀：只读与 SSH 隧道都是**环境级**（工作区 × 环境）的连接属性，交给 dbhub 自身的原生能力执行；插件不自行判定 SQL 是否可写、也不自建隧道实现。

- R59. 支持按环境开启**只读模式**，且只读必须由**上游（dbhub）原生拒绝**写操作来保证（返回 `READONLY_VIOLATION` 一类明确错误），不得以插件自制的 SQL 分类替代上游判定（避免与上游语义漂移、绕过面扩大）。只读是**逐环境**属性，不是插件级全局开关（"整体关停"由禁用承担）。**模型可以开启只读、绝不能关闭**：关闭只读必须由用户在配置页执行（否则模型等于自行提权），模型尝试关闭时应被拒绝并给出指引；界面上必须能看到哪些环境处于只读。开启只读不得使该环境的只读能力（如对象搜索）失效。
- R60. 支持为环境配置**手动 SSH 隧道**：主机、端口、用户、认证方式（密钥 / 密码）、密钥路径与口令、可选的**单跳** ProxyJump；隧道由 dbhub 原生能力建立，插件只负责收集、落库与传递。**隧道凭据（SSH 密码、密钥口令）只能由用户在界面输入，绝不进入模型上下文**；模型只能提供/修改非密字段（主机、端口、用户、认证方式、密钥路径、ProxyJump）并可解除隧道。编辑时秘密字段**留空表示保持原值**，已存秘密不得回显。隧道只支持**单跳**：多跳跳板机、`ProxyCommand`、ssh-agent 不予支持，命中时必须明确报"不支持"并给出指引，不得静默降级。插件**不复用也不读取**任何其他插件（包括 DSH 自带的 SSH 工具）的 SSH 配置。
- R61. 连接测试必须验证**有效连接**：即该环境在开启只读 / 配置隧道之后真正会被执行使用的那套连接（包含隧道与只读组合），而不是只测裸连接串；测试结果只是一次性反馈，不得改变连接状态、不得影响其他环境。测试取"待测连接"时**不得为此重扫全部工作区**：已保存的环境直接读持久化的连接，界面上已展示的环境用当前显示的那一行，只有从未扫描到的环境才做一次真实发现；测试进行中必须让等待**可感知**（显示已耗时）。宿主侧的探测预算必须严格低于浏览器侧的兜底等待（无隧道约 25 秒 / 有隧道约 45 秒，对应界面兜底 30 秒 / 60 秒），避免界面已超时而宿主仍在跑。
- R62. **dbhub 能力门槛**：只读与 SSH 隧道依赖 dbhub **1.4.0 及以上**的原生配置能力。检测到版本不满足时必须给出**明确错误与升级指引**（升级 dbhub，或改用插件自动安装的版本），**绝不静默降级**——尤其不得退回会被上游静默忽略的旧写法，否则会出现"看起来开了只读、实际仍可写"的危险状态。版本无法判定时放行，并在真实失败时给出指引；不满足门槛时配置页应禁用相关控件并说明原因，而不是等用户操作后才失败。
- R63. 自动发现的环境（未持久化，来自 mise env / .env）在被**显式**设置环境选项（只读 / SSH）时，必须把它**提升为持久化连接**（以当时解析到的连接串落库）并同时写入选项，且必须**明确告知用户**这次提升（此后该环境不再随源文件变化）；提升只能由用户或模型的显式操作触发——列出来源、执行查询、发布状态本身都不得触发持久化。
- R64. 必须提供**独立的 SSH 层连通性测试**（配置页行编辑器的「高级：SSH 隧道」区内、与「测试该配置」并列的「测试 SSH 隧道」），让用户能判断失败出在隧道还是数据库，并**如实说明它能证明什么、不能证明什么**：
  - 先拒绝不完整的隧道配置（缺主机、缺用户或缺凭据时不发起探测，直接说明缺什么）；**但「认证方式 = 密钥 + 密钥路径留空」不算缺凭据**：它按 SSH 客户端惯例落到默认身份文件 **`~/.ssh/id_ed25519`**（即该字段占位符显示的同一个值，插件侧常量 `DEFAULT_SSH_KEY_PATH`）。该默认**只作用于密钥认证且路径为空**：字段填了路径绝不覆盖，密码认证不受影响；「留空 = 保持原值」对秘密字段（密钥口令 / SSH 密码）与已存密钥路径照旧生效（已存路径存在时不会套用默认）。**保存与测试必须用同一条规则**——否则会出现"测试通过、保存却把隧道静默丢掉"，这正是修复前的现场。探测结论里必须**写明这次实际尝试的路径**（附一句"未填密钥路径，已按默认 … 尝试"），避免用户去猜是不是少打了一个字符。**诚实边界**：默认文件在那台机器上可能并不存在，此时结论应是可执行的 `SSH 密钥文件不存在或不可读：~/.ssh/id_ed25519`（并带同一句说明），而不是含糊的"配置不完整"；
  - 先做 **TCP 可达性**探测（插件宿主 → `ssh_host:ssh_port`，约 5 秒预算），给出「主机不可达 / 端口未开放」的明确结论并附**套接字错误码**（ENOTFOUND / ECONNREFUSED / ETIMEDOUT 等）——这一步单独就能把"DNS / 防火墙 / 端口"问题与其他问题分开；
  - 密钥认证时另做本地检查：私钥**文件存在且可读**；
  - 然后**故意**让 dbhub 对一个不可能在监听的地址（`127.0.0.1:1`）建立隧道，并**按证据判定，顺序固定且不得颠倒**：① 报错里出现 **SSH 层特征**（`SSH connection error` / `__dbhubSSHTunnelError` / 认证方式全部失败 / 私钥无法解析 / 加密私钥缺口令 / 握手 / ProxyJump / ssh2）时**单独即可判定隧道这一层断**（这类特征只会由隧道级问题产生）；② 否则出现 **数据库层特征**（`PROTOCOL_CONNECTION_LOST`、`Connection lost`、`server closed the connection`、`Access denied`、`Unknown database`、`ER_*`、`ECONNREFUSED`/`ECONNRESET`/`ETIMEDOUT`/`EHOSTUNREACH`、`SSH tunnel closed`）时判定**隧道可用**——驱动只有在转发连接建立之后才会说话（`SSH tunnel closed` + `Connection lost` + `PROTOCOL_CONNECTION_LOST` 正是"隧道通了、隧道后面的库不可用"的形状，且**不会**指名转发目标，所以"是否指名目标"不能作为唯一证据，这正是曾经的误判现场）；③ 否则若报错**指名了转发目标**，同样判定隧道可用；④ 两者都没有时才如实给「SSH 层结果无法判定」并附输出末尾，**不得猜测**；<!-- desensitize:allow （`__dbhubSSHTunnelError` 是 dbhub 自己的错误属性名，不是凭据） -->
  - **诚实边界（必须写明）**：该测试证明的是"网络可达 + 本地密钥就位 + SSH 层能否起来"，**不是**一次带真实数据库的完整 SSH 会话验证；隧道能建立不等于隧道后面那个库一定连得上（那仍由 R61 的有效连接测试回答）。
- R65. 连接测试失败时的**诊断必须分层归因，且只取 dbhub 输出的末尾**：
  - 诊断保留 dbhub 输出的**尾部**（多行、约 600 字符、保留换行原样展示）——致命行在输出的末尾，只取开头（如 dbhub 的启动横幅）会把真正的错误截掉，用户就看不出失败原因；尾部必须**丢掉栈帧行及其折行残片**（`    at …`，以及以 `file.js:L:C)` 结尾的续行），并按**行边界**截断：宁可少几个字符，也不得让消息以半行/半段路径开头（从半行开始的诊断读起来像乱码，也会让人误以为消息被截坏了）；
  - 配置了隧道时，消息前必须标出失败的层：「【SSH 层】隧道未建立：…」或「【数据库层】隧道可能已建立，失败发生在数据库连接/认证：…」；后者必须**措辞谨慎**（只能说"可能"），因为只有 R64 的独立测试才能证明隧道确实起来了；插件自身无法启动 dbhub / 生成配置时另用「【插件层】…」前缀（该情形既不属于隧道层也不属于数据库层）；同时必须给出可操作结论：**报【数据库层】即表示失败出在隧道后面的数据库（隧道这一层没有报错），用户不必再怀疑 SSH**——要把"可能"钉成确定结论，由 R64 的独立测试回答；
  - **用户名与密码都不得出现在诊断中**：dbhub 自身的横幅打印只掩了密码的 DSN（`mysql://root:****@host:3306/db`），因此清洗必须把**任意 URL 形态连接串的整个 userinfo** 折叠掉（`scheme://user:pass@host` 与 `scheme://user@host` → `scheme://****:****@host`），使诊断呈现为 `mysql://****:****@host:3306/db`。这是既有零知识契约的实际执行：密码与用户名不仅不得进模型上下文（R3），也不得出现在配置页的诊断文本里。
